# Part 1: Security, second pass

On 10-20 the first pass was shown: one client's records cannot be reached from
another client, sign-in limits, safe file downloads, backups and the recovery
plan. This is the second pass, done 10-21.

> **Say:** "Last time I showed the first security pass. Since then I did a
> second one, on two things: how long someone stays signed in and what a stolen
> session can do, and anything that leaves the app, like printing and CSV
> exports.
>
> **Signing in now works the way QuickBooks does, and in places it is
> stricter:**
> - Before, a browser stayed signed in for six months. Now a browser left alone
>   is signed out after an hour, with a two-minute warning. The firm can change
>   the hour. Everyone signs in again after 12 hours, whatever the setting.
> - Someone might copy the sign-in key off a computer and try to use it. The app
>   now notices an old key coming back, ends the session for both of them, and
>   records it in the Activity Log.
> - A code from the authenticator app works only once.
> - A firm admin's temporary password for a new login is only good for choosing
>   a real one. Passwords like `Password2026!` are refused.
> - The firm can require the second step for every login. I'd like to turn that
>   on before November 1.
> - Guessing your own password from inside a session, on Change password, now
>   counts toward the five-try lock.
> - Taking a firm admin's role away now works at once. Before, it lasted up to
>   15 minutes.
>
> **What leaves the app:**
> - The print pages for deposits, checks, expenses and the Transactions search
>   pasted names in without escaping them. A vendor name read off an emailed
>   invoice could have run code. They now print like the reports do.
> - In a CSV export, a cell starting with `=` is a formula to Excel. It is now
>   kept as text.
> - The web app and the API send the headers a banking site sends. Nobody can
>   frame the app, nothing is cached in the browser, and everything goes over
>   HTTPS.
>
> **Behind the scenes:**
> - The AI reads at most 200 documents an hour per login, since each one costs
>   money.
> - The live server refuses to start with the example secrets.
> - Two packages with known holes were updated.
>
> All of these have automated tests except the server's check on its secrets,
> and it has all been live since Thursday."

Show these four. Each takes under a minute.

- [ ] **1. A new login chooses its own password.** In the private window, sign
  in as the test login with the password Invite showed. Only "Finish setting up
  your login" opens. Type `Password2026!`: it is refused. Choose a real one, and
  the app opens.
- [ ] **2. A role taken away stops at once.** In your window, Setup → Users:
  make the test login a firm admin. In the private window, open Setup → Users:
  it opens. Back in your window, change it to Staff. In the private window, open
  Setup → Users again: "Only a firm admin can do this."
- [ ] **3. Require the second step.** Setup → Users → Sign-in security. Before
  it is ticked, the card says how many logins have not set the second step up.
  Tick "Require the second step for every login". In the private window, sign out and in again: the test login is
  asked to set up the second step before anything else. Untick it afterwards
  unless the firm decides to keep it (see "To ask").
- [ ] **4. Signed out when left alone.** Show the "Sign out a browser left
  alone for" setting (15 minutes to 3 hours; 1 hour by default). Waiting is too
  slow for the meeting, so tell it: a "Still there?" box counts down the last
  two minutes, and the sign-in page then says why.

Tell, without clicking:

- [ ] **5. CSV.** A test vendor named `=1+1`, exported from Transactions and
  opened in Excel, reads `=1+1`, not `2`. Show this live if Excel is to hand.
- [ ] **6. A copied key ends the session.** If one shows up, Setup → Activity
  Log says "Session ended: an old sign-in key was used again".

# Part 2: Is the app secure now?

> **Say:** "The honest answer is that no system is ever fully secure, and we
> shouldn't promise that to a client. QuickBooks doesn't either. What I can say
> is this. The code has had two full security reviews, and everything they
> found is fixed, with tests that run on every change. On top of what was
> already there (five roles, logins that lock after wrong passwords, two-step
> sign-in, an activity log of every change, SSNs and tax IDs encrypted), the
> first pass made sure one client can never reach another client's records.
> The second pass is what I just showed.
>
> What's left isn't code, it's how we run it. There are four things to do
> before November 1, and with those done it is secure enough for the firm's own
> team to use on its clients' books. Before outside customers come on in
> January, there are a few more, and I'd want someone who didn't build it to
> test it."

**Before November 1** (real client data):

| What | Why | Who |
|---|---|---|
| Take the first production backup and prove it restores (`docs/guides/backups.md`). Decide how often, and where copies go: off Railway and off any one laptop | No backup of production exists yet. Railway takes none on a schedule on the Hobby plan; scheduled backups need Pro | Aheed, firm |
| Copy `FIELD_ENCRYPTION_KEY` and the JWT secrets into a password manager the firm controls | Without that key, a restored database cannot read SSNs, tax IDs or anyone's two-step secret. Nothing gets them back | Firm admin |
| Turn on "Require the second step for every login" (step 3) | A stolen password alone then gets nobody in | Firm decides |
| Decide where uploaded files live: Cloudflare R2 (the code is ready) or scheduled copies of the Railway volume. Check the API has a volume at all | Attachments, receipts and check stubs are in no backup today | Aheed |
| Read Railway's notice on its 10-22 incident. If it says to rotate secrets, change the JWT secrets (everyone signs in again) and the database password | Railway's status page tied the outage that day to a security incident | Aheed |
| Check that Setup → Activity Log shows each person's own address, not one address for everyone | The sign-in limit per address relies on it | Aheed |

**Before January 1** (outside customers):

- **Switch the script policy from report-only to enforced.** Do it once the
  Railway log has shown no `[csp]` lines for a few days. It is the second line
  of defence against injected script.
- **Replace the spreadsheet reader** (`xlsx` 0.18), which has a known hole, with
  SheetJS 0.20.3.
- **Serve the API under the app's own domain** (a custom domain). Then the
  sign-in key does not have to sit in the browser's storage.
- **Set up a standby copy of the database.**
- **Get an outside security test (penetration test)** before strangers' books
  are in it.

> **Say:** "Most of Faizan's second video showed things we'd already changed,
> like Reverse, Back to practice and the account types. That's because the live
> site had stopped updating. Netlify, which serves the screens, stopped picking
