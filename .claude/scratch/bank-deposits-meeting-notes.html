01

What was actually broken

The feature had never been exercised against real data — every one of these would have surfaced the first time someone tried to use it.

Deposits could never post journal_entry_source_type enum

The Postgres enum backing journal entries never had 'bank_deposit' added to it. Creating any deposit would crash the moment it tried to post its journal entry.

Zero deposits existed in the database before this fix

"Make Recurring" rejected every attempt recurring_template_type enum

Wired up on the frontend, but the backend's enum migration tried to add 'deposit' via a text CHECK constraint on what is actually a real Postgres enum column — a no-op that would fail on first use.

Every "Save template" click would 500

Deleting a deposit never worked deleteDeposit()

Missing a source_guard when voiding the journal entry, so the void was rejected as "source-generated" — for every deposit, not just edge cases.

Delete was dead on arrival for any deposit

Cash-back validation was unreachable code

"Cash back exceeds total" can only be true when the net total is already ≤ 0 — a different check that always fired first, so the specific message never actually showed.

Caught by writing the first real test for it

The bank account dropdown was always empty GET /bank-accounts

The endpoint returns { bank_accounts: [...] }, but the page checked Array.isArray(response.data) — false for that shape, so the list silently resolved to empty every time.

Broke account auto-select on new deposits too, not just editing
02

The GL drill-through investigation

Clicking a "Deposit" row in the General Ledger opened the raw Journal Entry screen. Tracing it to the database, not just the code, found the real shape of the problem.

All 117 existing deposits came from AI coding, not manual entry

Every "Deposit" row in the GL was posted by the bank-statement AI coding pipeline (emailImports.ts) — none were backed by an actual deposit record, because that table didn't exist in this database yet.

5 of 7 businesses had never registered a bank account

They were importing statements and posting deposits against a GL cash account, but no bank_accounts row existed to tie a deposit record to.

03

What was built

Deposits are editable after posting

Date, memo, bank account, other-funds lines, and cash-back can now be changed post-save — previously the page only supported create and read.

Recurring deposits work end-to-end

Schema, service, and scheduler gating fixed; added a manual "Run now" action so unscheduled/reminder templates are actually usable, not just stored.

AI-coded deposits now wrap into real deposit records

Non-destructively — the original journal entry and its link back to the import batch are untouched. Happens automatically going forward; backfilled for all 117 historical entries.

Every deposit opens directly in edit mode

No separate view vs. edit screen, same as QuickBooks — including AI-imported ones. The "Imported" badge is now informational only; change anything and hit Save, it overwrites in place.

"Recent Deposits" history popover

The clock icon top-left now opens a dropdown of the 10 most recent deposits (date + amount), click-through to any of them — matching the QuickBooks pattern.

New validation rules

Can't deposit into the same account you're depositing from; every line needs an account; cash-back can't exceed the deposit total.

04

Worth raising in the room

  • Bank accounts were auto-created for the 7 businesses that never had one — named from the GL cash account their deposits already use. Worth a quick sanity check on the names.
  • Editing a deposit doesn't let you change which Undeposited Funds payments are included — a deliberate simplification, not an oversight; that set stays fixed once posted.
  • The "Balance" shown next to the account is the bank-feed balance, not the book balance — reads $0.00 for any account that's never had a CSV statement imported, even with real deposits posted against it. Not yet fixed; flagging for a decision on which number belongs there.
  • No PDF deposit slip yet — Print still opens the browser print dialog rather than generating a formatted PDF.
05

Chasing the 10-second delay

Every click into a deposit took 10–15 seconds. Several plausible-sounding diagnoses — including ones pasted in from other tools — got tested against the real system and discarded before the actual cause surfaced. Worth walking through, since the method is as reusable as the fix.

CORS was blocking the one test that would have settled it early

Testing a production build (vite preview, port 4173) couldn't even log in — that origin wasn't in CORS_ALLOWED_ORIGINS. Fixed first so a real dev-vs-production comparison was possible at all.

Pool size and raw query speed both checked out

25 concurrent queries fired through the exact production pool config (max: 10) finished in 789ms total. Individual queries — including the full General Ledger query chain — ran 100–130ms direct against the real database. Neither explained a multi-second delay, let alone ten.

Live instrumentation proved the database wasn't the bottleneck

Added real request timing and DB pool utilization logging directly to the running server. Result: waiting: 0 on every single slow request — idle, available connections sitting unused for the full 10+ seconds. Whatever was slow, it wasn't Postgres.

Root cause: 50 routers, each quietly re-running tenancy middleware

Every route file mounts its own router.use('/businesses/:businessId', requireAuth, resolveBusiness). Express matches that as a path prefix, so a request to a late-mounted router silently re-triggers every earlier-mounted router's auth + tenancy DB lookups first. bankDepositsRouter sits 61st of 61 — about 60 redundant round trips stacked in front of the real handler. Mount position predicted delay severity exactly.

Every route in the app was paying this tax, proportional to mount order

Two-line fix, app-wide benefit

Both middlewares now short-circuit when the request has already been authenticated / resolved earlier in its own chain — safe, since the JWT and businessId don't change mid-request. No router files touched.
